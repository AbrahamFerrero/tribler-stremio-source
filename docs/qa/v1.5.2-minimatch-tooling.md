## Causa raíz y corrección exacta

`defaultStreamRankingPolicy` ejecuta el loader al importar ranking-policy. La incorporación de `{ cause: error }` preserva correctamente el error original, pero los imports estáticos de app/config en index se evaluaban antes de su try. Al fallar esa evaluación, Node inspeccionaba la causa y su stack automáticamente en stderr. Un probe sintético confirmó que el marcador de la causa no se emitía con el código exacto de ranking-policy de v1.5.1 y sí con la candidata anterior.

En `src/index.ts` se mantienen estáticos dotenv y el logger seguro. `main()` es ahora async y carga app y config, en ese orden, mediante imports dinámicos. `void main().catch(...)` reutiliza el diagnóstico existente `Startup failed` con safeErrorDetails y exitCode 1. Se capturan tanto rechazos de importación como errores síncronos posteriores al await. El servidor, cleanup y handlers SIGINT/SIGTERM no cambian.

La compilación CommonJS transforma esos imports en cargas require dentro de una promesa; el rechazo llega al catch final. Los tests compilan el programa productivo real en un directorio sintético y ejecutan ese index.js, además del código TypeScript: no dependen de un dist previo ni de un mock de main.

El logger sigue disponible antes de las cargas problemáticas. Su cadena url-policy → dns/http-privacy no importa config, app ni ranking-policy. No hay un ciclo hacia el módulo de política.

Los nueve CLI con la misma fuga reproducida añaden únicamente un import temprano de `src/startup-policy-guard.ts`. Esta guarda hace una carga síncrona **acotada a la política** con createRequire dentro de try/catch, registra el mismo diagnóstico seguro y termina con código 1 si falla. Las cargas posteriores reutilizan la caché de CommonJS; no se relee la política por el nuevo control.

La alternativa síncrona conserva los exports de helpers y el orden de evaluación de esos CLI CommonJS y del CLI mjs con interop de tsx, sin envolver ni mover sus implementaciones completas. La frontera que puede terminar el proceso solo se activa cuando el ejecutable está en scripts/; importar los helpers como biblioteca mantiene su contrato ordinario. No hay una exclusión por entorno de test. Los tests existentes de helpers y los subprocesos reales de cada CLI acreditan ambas rutas.

Dotenv sigue primero en los ejecutables que ya lo cargaban estáticamente. qa-identity-conflict-review conserva su carga explícita de dotenv posterior a los imports, y soak no incorpora dotenv. No se cambian los catches y formatos de salida existentes de operaciones que alcanzan main.

No se añaden uncaughtException handlers, filtros de stderr ni reglas desactivadas. Error.cause se conserva en los cuatro wrappers internos. La corrección controla quién inspecciona el error; no borra causas ni altera safeErrorDetails.

Cada uno de los nueve CLI añade solo el import de la guarda antes de las otras dependencias de aplicación. La guarda completa es:

```ts
import { createRequire } from "node:module";
import { dirname, resolve } from "node:path";
import { logger, safeErrorDetails } from "./logger";

// Preserve synchronous CLI helper exports and their ordinary import contract.
// Only an executable in scripts/ owns this process-exit boundary. Its remaining
// static imports reuse the successfully initialized CommonJS policy module.
const entrypoint = process.argv[1];
if (entrypoint && dirname(resolve(entrypoint)) === resolve(__dirname, "../scripts")) {
  try {
    createRequire(__filename)("./streams/ranking-policy");
  } catch (error) {
    logger.error("Startup failed", { error: safeErrorDetails(error) });
    process.exit(1);
  }
}
```

## Reglas, archivos y privacidad

La comparación final inspecciona **252 archivos**, conserva los **248 de v1.5.1** y añade la guarda y tres archivos de tests. Cero errores y avisos. No se cambia eslint.config.mjs, no se elimina un archivo ni se reduce severidad de reglas anteriores. Las reglas nuevas no-unassigned-vars, no-useless-assignment y preserve-caught-error permanecen activas.

La comparación por archivo de reglas y opciones figura en el inventario. Las reglas tipadas mantienen sus opciones. Los cambios de defaults core de la migración son reportGlobalThis true en no-shadow-restricted-names, checkRelationalComparisons false explícito en no-constant-binary-expression y defaults adicionales de no-unused-vars core ya desactivada. disableTypeChecked añade no-unsafe-enum-assignment off en los ocho archivos previamente sin reglas tipadas; no estaba activada en la base.

Tests negativos verifican no-explicit-any, no-unused-vars, no-unsafe-assignment/call/member-access/return, no-floating-promises, no-misused-promises, await-thenable y no-undef; se mantiene un caso tipado correcto como control.

La regresión original mantiene la exigencia de código 1 y ausencia del marcador de causa/stack. Se reemplazó únicamente su expectativa del mensaje crudo por la expectativa del diagnóstico sanitizado exacto, que es el comportamiento autorizado. No se quitó la condición que detectaba la fuga.

Las pruebas adicionales verifican los diez ejecutables y CommonJS, sin marcador, mensaje interno, rutas fixture ni rechazo no gestionado en stdout/stderr. También verifican dotenv válido, puerto/host de configuración, listener real en puerto efímero y apagado único ante SIGINT/SIGTERM repetidos. Toda la red de esos fixtures está interceptada; no se usan proveedores ni configuración privada.

Los tests previos de privacidad siguen comprobando identidad de cause y mensajes externos, cause no enumerable, safeErrorDetails sin acceso a stack/cause/getters hostiles y conservación de code/status permitidos. La ruta real de deshabilitación de addons, el middleware HTTP y los logs no exponen internals; JSON/HTML rechazan campos cause/stack/error ajenos al esquema cerrado. El escáner mantiene exit 1 y mensaje externo ante lstat EACCES sintético sin imprimir su causa.

Frente a v1.5.1, el nuevo marcador de causa ya no se emite y las excepciones de inicialización del arranque principal llegan ahora al diagnóstico seguro existente. No se borran datos internos de la excepción ni se suprimen campos legítimos de safeErrorDetails.

## Runtime y tooling

La aplicación conserva **Node >=20**. Error.cause ya existe en Node 20; ni esta corrección ni sus dependencias productivas necesitan elevar ese mínimo. No se cambió engines.

Instalar todas las dependencias y ejecutar ESLint 10/@eslint/js 10 requiere **^20.19.0 || ^22.13.0 || >=24**. Es un requisito de desarrollo distinto del runtime productivo: Node 20.0–20.18 y 22.0–22.12 cumplen el engine de la aplicación pero no el del tooling. Se probaron 20.19.0 y 22.23.2 reales, con suites completas en ambos; no se presume cobertura de todas las versiones o plataformas.
