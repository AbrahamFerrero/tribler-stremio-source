## Diseño y rutas de fallo

La etiqueta no forma rutas ni activa comprobaciones. Se rechazan etiquetas vacías, traversal, separadores, caracteres de control y valores demasiado largos antes de crear evidencia. Cada ejecución crea `.cache/story2/runs/run-<aleatorio>` mediante mkdtemp, después de rechazar symlinks/junctions/reparse points en los componentes controlados. Las rutas de informes de Vitest se generan dentro de ese espacio exclusivo y se verifican antes de lanzar el proceso. Python no realiza cleanup recursivo ni retira ejecuciones anteriores.

La garantía presupone que otro proceso con los mismos permisos no sustituye maliciosamente directorios durante las comprobaciones. No existe una garantía de confinamiento frente a un atacante que controle el sistema de archivos del usuario. La ausencia de un sandbox OS es explícita.

Los logs y archivos iniciales usan creación exclusiva. El manifest se publica mediante archivo temporal exclusivo, fsync y os.replace. Se distinguen RUNNING, FAILED, SUCCESS y BASELINE_CHARACTERIZED. Si el proceso muere antes de publicar el resultado, un manifest RUNNING es incompleto; nunca se reutiliza otra ejecución con la misma etiqueta. Si el disco impide registrar el fallo, permanece el estado incompleto anterior. No se promete rollback del sistema de archivos: se preserva evidencia aislada sin promoverla a éxito.

La restricción de procesos es específica de este runner. En Windows el lanzador Python no crea Node hasta estar dentro del Job Object privado; el cierre del handle termina sus descendientes. No se mata por nombre ni se enumeran PIDs ajenos. En POSIX, start_new_session crea un grupo propio y el monitor del pipe del padre cubre su cierre; los hijos cooperativos se terminan por ese grupo. El código POSIX está preparado para CI, pero no se certifica ejecución Linux desde este entorno Windows.

Referencia del mecanismo Windows: [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). No se construye un sandbox OS ni un servicio persistente de procesos.

## Límite efectivo de entorno

El probe no hereda el PATH completo, NODE_OPTIONS, tokens ni HOME/APPDATA del usuario. Usa directorios propios y un PATH formado por las ubicaciones explícitas de Node, Python, Git y herramientas del sistema. Los tests también aplican ese entorno a sus subprocesos.

La fixture crea su propio `.env` con `VITE_MAGICAST_DISK_CANARY=placeholder-disk-canary`. Un control positivo comprueba que la API real de Vite lo cargaría. La ejecución de Vitest declara envDir=false y verifica que ni ese valor ni el canary de entorno del padre lleguen al test. Se mantiene DOTENV_CONFIG_PATH dirigido a una ruta propia sin configuración.

Esto evita las cargas automáticas auditadas; no impide que código Node/Python ejecutado con los permisos del usuario lea otros archivos o use red. No se inspeccionaron ni publicaron valores de configuraciones privadas. La validación completa se ejecuta en exportaciones source-only nuevas, sin copiar `.env`, `.private-runtime`, perfiles, corpus locales o caches privados. La configuración funcional y de cobertura original permanece intacta.
